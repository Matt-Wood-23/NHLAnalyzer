Before you pull

Back up the prediction log first

One of these commits stops tracking data/predictions/prediction_history.parquet in git. It is the only file here that cannot be rebuilt — everything else regenerates from MoneyPuck.

  1. Copy the log somewhere safe.

    cp data/predictions/prediction_history.parquet \
   ~/nhl_history_backup.parquet

  2. Pull, then check the file survived. If git reports a conflict on that path, resolve it with git rm --cached data/predictions/prediction_history.parquet — the working file stays put.

    git pull
ls data/predictions/

  3. Rebuild and see the real numbers. The daily run now also builds the player stats the props fix depends on.

    python -m pipeline.daily
python -m pipeline.evaluate_history --season 2025-2026

What was broken

Fixed

Season dates were a year behind, blanking a whole season of features

The start-date table in features/context.py ended at 2024–25. Every 2025–26 game got a null date, so rest days, back-to-back and season-day were NaN across the newest season of training data. No error, no warning.

The season list, current season and opening dates lived in ten files in three different formats. They now derive from one table in config/season.py. Rolling to a new season is a one-line edit, and forgetting it degrades to an October estimate with a warning rather than nulls. A test fails the build if any module hardcodes a season literal again.

Fixed

Live predictions used features the model was never trained on

Training rolled team stats strictly within a season. The live pipeline re-implemented that logic and rolled across season boundaries, with a different venue-split window. Worst in October, when every carried-over value came from the previous season.

Serving features are now produced by appending a placeholder row to the history and running the same function that builds the training matrix. Verified identical across all 70 team columns and all 8 player columns. Keep this pattern: add a feature to the training function and let the snapshot inherit it, rather than computing it separately on the serving side.

Fixed

/props was running on 5 of its 11 features

Six features were hardcoded to NaN, commented “not in NHL API”. True — but the SOG model doesn’t train on the NHL API. It trains on player_game_stats.parquet, built from MoneyPuck shot data already sitting on disk, which carries per-player expected goals.

More than half the model’s inputs were replaced by training-set averages on every projection. Coverage went 45% → 100% in testing. The parquet was also only ever built by running ingestion.player_stats by hand, so the props training data had been drifting out of date with everything refreshed daily beside it — backfill and daily now rebuild it.

Fixed

/history rewrote a data file every time it was called

The Discord command called backfill_outcomes(), writing to the prediction parquet on every invocation — racing the daily pipeline. Re-scoring could also erase stored outcomes whenever the feature matrix was absent.

Scoring is read-only in the bot now; the daily pipeline owns the writes. Played results are preserved and only refreshed, never dropped.

What /history shows now

It reported a lifetime accuracy number with nothing to read it against. Home teams win roughly 54% of NHL games, so accuracy alone can’t tell you whether the model found anything.

  • Baselines. Accuracy against always-picking-home, Brier against the no-skill score, both from the same games.
  • Season-scoped. Seasons are derived from the game ID, so 2026–27 won’t pool into 2025–26. Works retroactively on rows already logged.
  • Calibration, which the report already computed but the bot never displayed.
  • Pick-strength breakdown, answering the question the Strong Pick / Lean / Toss-Up labels invite. The labels and the breakdown now share one definition, so it genuinely checks them.

Verified & not

Everything below was tested end-to-end on synthetic data — no network, no Postgres.

  • Context features are populated across every season, including the newest. The date bug is gone.
  • Training and serving agree on every feature column, in both the game and props pipelines.
  • ELO carries no leakage, stays zero-sum, and reproduces the old behaviour exactly at ot_win_value = 1.0.
  • An old-format history file upgrades with no row or outcome loss.

Still needs your real data:

  • Whether the overtime discount actually helps. Roughly a quarter of games are decided after regulation and those are near coin flips, but crediting them as full wins was pushing that noise into the model’s most important feature. Unvalidated — python -m features.elo will settle it, and the old behaviour is in the tuning grid so it can only win if it deserves to.
  • Whether any of this changes real accuracy. The parity fixes are correctness fixes, not guaranteed accuracy wins.
  • The numbers I quoted earlier. 55.7% against a 57.1% baseline, Strong Picks at 72%, Leans at 39% — all from the stale 85-row March snapshot in the repo, not your season. Illustrative only. Re-derive them on the real log.

Two things that will bite

  • The saved model files are tracked in git. Running pipeline.train or models.sog_model overwrites models/saved/*.pkl. I clobbered them twice while testing and had to restore from git. Check git status after any training run.
  • The repo is no longer a backup for the prediction log. Back it up elsewhere and carry it across machines.

Open items

Confirmed goalie starters

largest accuracy gain

The pipeline uses each team’s most recent starter. Actual starters are announced pre-game and backups start roughly a third of games. Goaltending is among the biggest single-game swing factors. Needs a reliable pre-game source.

Odds and closing-line value

answers “beat the market”

ingestion/odds_api.py is complete, working, and imported by nothing — and it’s Postgres-only, so it can’t run in the Parquet setup you actually use. The free tier needs no card and is enough to log closing lines going forward, though it can’t backtest 2021–26. If odds aren’t wanted, delete the file rather than leave dead code implying a working feature.

Check whether DATABASE_URL is set

one command

Without Postgres, h2h_home_win_rate_l3 is NaN in both training and serving — a permanently empty input. If it’s unset, either reimplement head-to-head on Parquet or drop the feature.

Automating the daily run

PC or Pi

pipeline.daily already does the whole loop, so either target is a single cron line. What’s missing for unattended operation: a lockfile so overlapping runs can’t both write the parquets, failure notification through the Discord webhook, and retry on network blips during the download. The Pi’s real constraint is the pandas rebuild over five seasons of shot data.

Smaller

when convenient

Two live snapshots still reach across season boundaries, which only shows in the opening week. Props still projects scratched players. And 290 features on ~5,000 games is a lot — trimming to the top 20 improved Brier from 0.2416 to 0.2404, which suggests most of the rest is noise.
