Where the Pipeline Runs

Four ways to take the daily run off your desk, with what each one actually costs. Every number here was measured on the repo, not estimated.

The choice is shaped by two jobs, not one

This is the thing that decides the answer, and it isn’t obvious until you look at what has to stay running.

The daily run

starts · finishes · exits

Refresh MoneyPuck, rebuild the feature matrix and boxscore spine, score yesterday’s picks, predict today’s slate, post to Discord. Roughly 2–4 minutes, once a day.

The Discord bot

runs forever · holds a socket

--bot mode keeps a websocket open to Discord so the nine slash commands answer. Today that only works while your PC is on and the process is running.

So the real question is whether you want the slash commands. If webhook posts are enough — predictions, props, saves, edges and results pushed to a channel on a schedule — GitHub Actions covers everything and needs no machine at all. If you want /edge and /yesterday to answer on demand, you need a host that stays up, and at that point it may as well also run the daily job.

The 20 KB is the whole reason this is easy. The one file that cannot be rebuilt from source data is prediction_history.parquet — it records what the model believed before each game was played. The options in full

GitHub Actions

Least effort · no bot

A scheduled workflow on GitHub’s runners. You already have .github/workflows/tests.yml working, so the mechanism is proven here. Free and unlimited because the repo is public.

It fits unusually well because the state problem — the hard part of automating anything — is 20 KB of git-tracked Parquet. The workflow commits the log back after each run, so you get a versioned history of every prediction as a side effect. That is strictly better than a local file you could overwrite.

The three gaps in the current setup map onto built-in features rather than code: a concurrency group replaces the lockfile, failure email plus an if: failure() webhook step covers notification, and only the MoneyPuck download needs retry logic since everything else is idempotent. actions/cache holds the 451 MB, well inside the free 10 GB.

What you accept

Scheduled runs are queued, not punctual. Free-tier crons typically fire 5–20 minutes late and occasionally worse. Schedule with margin — 21:00 UTC leaves about two hours before puck drop.

GitHub disables schedules after 60 days of repository inactivity, which solves itself here since the workflow commits daily. The cache evicts after 7 unused days; daily runs keep it warm, and a miss just costs one slow run. And no slash commands, ever.

Oracle Cloud Always Free

Most capable · hardest to obtain

An always-on Linux VM you own. The headline allowance is 4 OCPUs and 24 GB RAM on Ampere ARM, splittable across up to four instances, free with no expiry. An OCPU is a full physical core, not a hyperthread, so that is genuinely four cores. No other major cloud’s free tier is within an order of magnitude.

Alongside it: 200 GB block storage, 20 GB object storage and 10 TB/month egress. Your entire project is 451 MB, so you would use a rounding error of the storage.

For this project it does all three things — the daily cron, the Discord bot as a systemd unit, and Postgres properly, so the DATABASE_URL path stops being the optional branch it is today. Cron on your own box also means 17:00 means 17:00. And with four cores you can retrain there too, which sidesteps the pickle-version problem below entirely.

What you accept

Getting an Ampere instance is the real hurdle. “Out of host capacity” is a long-running, widely-reported frustration; popular regions can be dry for days. Mitigations: choose a less-saturated home region at signup, script the create call and retry on a loop, try off-peak. Budget more than one sitting. Your home region is fixed at signup and Always Free resources only live there, so choose deliberately.

Idle instances can be reclaimed. Roughly: over a 7-day window, CPU 95th-percentile under 20% with low network and memory. A bot plus one daily job may well look idle by that standard. The usual fix is upgrading to Pay As You Go — Always Free resources stay free and PAYG accounts are exempt — but that means a card on file and real exposure if you provision past the free limits. Set a budget alert at $1 the same day if you go that route.

A credit card is required at signup even for Always Free, and free resources carry no SLA. Verify the current allowances on Oracle’s page before committing; these figures are from training data, not from checking today.

Your PC, via Task Scheduler

Working tonight · least durable

The data is already here, the environment already works, and Windows Task Scheduler can wake the machine for a task. Setup is one scheduled task and, if you want the bot, one startup entry. Nothing new to learn and nothing that can be reclaimed by a cloud provider.

The honest case for this is that it is reversible. Run it for a month, find out whether you actually use the slash commands, then move to something else knowing what you need.

What you accept

The machine has to be awake at the scheduled time every day, and there is no failure notification unless you build one — a silent failure looks identical to a quiet night with no games. If the pipeline stops, you find out when you notice the channel has gone quiet.

Raspberry Pi

Always-on you control

Always-on, low power, no provider who can reclaim it. Correcting something I said earlier: the ARM concern was wrong. Every dependency — scikit-learn, XGBoost, LightGBM, pyarrow, SciPy — ships aarch64 wheels or is pure Python, so the install is unremarkable.

What you accept

RAM is the real constraint if you ever want it to train rather than just serve — the feature matrix is 6,877 × 295 and the tuning runs are heavier still. Serving a pickle is comfortable on any recent Pi; retraining is not what the hardware is for.

It is also another physical box to patch and keep online, for capability Oracle gives free. Worth it mainly if you want the hardware anyway or prefer nothing running in someone else’s cloud.

One thing that applies to every remote option

Model pickles are version-sensitive. Train with one scikit-learn on Windows and load with another on Linux, and joblib will warn or fail outright. Two ways out: pin exact versions in requirements.txt, or train on the same box that serves. Oracle can do the latter comfortably; a Pi cannot; Actions would need the pinning.

How I’d decide

Answer one question first: do you want the slash commands, or are scheduled webhook posts enough?

  • Webhook posts are enough → GitHub Actions. It is free, needs no machine, cannot be reclaimed, and the failure notification you are missing is a built-in feature rather than something to build.
  • You want the bot answering on demand → Oracle, with your PC as the stopgap while you fight for an instance. Oracle then runs the cron, the bot and Postgres, and the punctuality is a real bonus over Actions’ queue.
  • You want to decide by using it → Task Scheduler this week. It costs an hour, tells you whether the slash commands matter to you, and throws nothing away.

Given that you want a box for other things regardless, Oracle is the better single answer — it covers all three jobs where Actions covers one. The counterargument is purely operational: Actions is zero-maintenance and cannot be taken away, and a VM is a thing you own and patch forever.

Most of the work is portable. The systemd unit for the bot, the cron entry, the lockfile and the failure-notification hook are identical on Oracle, a Pi, or any other Linux host. Only the GitHub Actions path is genuinely different. So the decision can be deferred without deferring the work — and if the answer turns out to be Actions, the workflow is short.
